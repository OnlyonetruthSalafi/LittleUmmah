## 1. งบโควต้า Claude — หลักคิด

### 1.1 สิ่งที่รู้และไม่รู้

- Claude **อ่านโควต้าตัวเองไม่ได้** และไม่รู้แพ็กเกจของเจ้าของโปรเจกต์ ตัวเลขข้างล่างจึงเป็น **ค่าประมาณเริ่มต้น**
  ไม่ใช่ขีดจำกัดที่คำนวณได้จริง — ต้องปรับหลังสัปดาห์แรก (ข้อ 1.5)
- โควต้ามีสองชั้น: **หน้าต่าง 5 ชั่วโมง** (หมุนเวียน) และ **เพดานรายสัปดาห์** — ชั้นรายสัปดาห์คือตัวที่ชนจริงเมื่อใช้ทุกวัน
- Codex มากกว่า 20 เท่า → เป้าคือ **Claude ใช้ราว 5% ของแรงงานทั้งหมด** (1 : 20)

### 1.2 หน่วยนับ: "แต้ม Claude" (C)

1 C ≈ งานขนาดเล็กหนึ่งชิ้นของ Claude (อ่านไฟล์ไม่กี่ไฟล์ + ตอบหนึ่งครั้ง)

| กิจกรรมของ Claude | แต้ม | วิธีลดแต้ม |
|---|---|---|
| เขียน brief หนึ่งแพ็กเกจ (ใช้แม่แบบข้อ 5) | 1–2 | ใช้แม่แบบ ไม่เขียนใหม่ทุกครั้ง |
| ตรวจรับงาน non-religious | 1–2 | รัน `npm run verify` คำสั่งเดียว อ่านรายงาน Codex + diff เฉพาะจุดเสี่ยง |
| ตรวจรับงานที่แตะ UX/ภาพใบหน้า | 2–3 | Codex ส่งภาพ crop ศีรษะ/ขนาด DOM มาให้ ไม่ให้ Claude เปิดเบราว์เซอร์เอง |
| **ตรวจเนื้อหาศาสนา 1 ชุด** (เช่น ดุอาอ์ 5 บท, ความหมายอายะฮ์ 10 ท่อน) | **4–6** | Codex เตรียม "ชุดหลักฐาน" (URL Shamela + ตัวบท + เลขหน้า) Claude **เปิดยืนยันเอง** แต่ไม่ต้องค้นเอง |
| รวมงานเข้า branch + แก้ conflict | 1–3 | Codex rebase และรัน verify ก่อนส่ง |
| สรุปให้เจ้าของโปรเจกต์ | 1 | ใช้รายงานรูปแบบตายตัวของ Codex |
| วางแผน/ตัดสินโครงสร้างใหม่ | 3–5 | ทำครั้งเดียวต่อระยะ |

### 1.3 งบตั้งต้น

| ช่วง | งบ | กันสำรอง |
|---|---|---|
| **ต่อหน้าต่าง 5 ชม.** | ~12 C → เช่น ตรวจศาสนา 1 ชุด + ตรวจรับ 2–3 แพ็กเกจ + brief 1–2 ชิ้น | 20% (~2–3 C) สำหรับงานด่วน/แก้ conflict |
| **ต่อสัปดาห์** | ~5 หน้าต่างที่ใช้งานจริง ≈ 60 C | 10% (~6 C) |

**การแบ่งงบรายสัปดาห์**

| หมวด | สัดส่วน | ≈ C/สัปดาห์ |
|---|---|---|
| ตรวจเนื้อหาศาสนา (คอขวดที่มอบให้ใครไม่ได้ — `AGENTS.md` ข้อ 4) | 40% | 24 → **ไม่เกิน 4 ชุดต่อสัปดาห์** |
| ตรวจรับ + รวม branch | 30% | 18 |
| brief + วางแผน | 15% | 9 |
| สรุปเจ้าของโปรเจกต์ | 5% | 3 |
| สำรอง | 10% | 6 |

### 1.4 กฎประหยัดโควต้า Claude

1. **Claude ไม่ทำงานแรงงาน** — ไม่ refactor เอง ไม่วัด DOM เอง ไม่เปิดเบราว์เซอร์เอง ไม่ร่างคำแปลเอง
2. **งานศาสนารวมเป็นก้อน** ทำในหน้าต่าง 5 ชม. ที่กันไว้เฉพาะ อย่าตรวจทีละบรรทัดกระจายหลายวัน
3. **Codex ทำงานต่อเนื่องได้โดยไม่รอ Claude** — ต่อคิวไว้ 3–5 แพ็กเกจล่วงหน้าเสมอ
4. **รายงาน Codex สั้นและตายตัว** (ข้อ 5.2) Claude อ่านรายงาน ไม่อ่าน log ยาว
5. **CI แทน Claude รันตรวจซ้ำ** — หลัง P0-2 Claude รันแค่ `npm run verify`
6. Claude เรียก `codex exec` แบบ background ได้ แต่ **ห้าม poll** — รอแจ้งเตือนเมื่อจบ

### 1.5 การปรับงบ

- ต้องมีบันทึกให้เทียบ ไม่งั้นปรับไม่ได้ — ใน `docs/briefs/QUEUE.md` (สร้างใน P0-4):
  - ตารางคิวมีคอลัมน์ **"C ที่ใช้จริง"** Claude กรอกเมื่อปิดแต่ละแพ็กเกจ
  - บรรทัดรายสัปดาห์ **"usage Claude ที่เจ้าของโปรเจกต์เห็น: __% (5 ชม.) / __% (สัปดาห์)"**
- หลังสัปดาห์แรก Claude เทียบผลรวม C กับ % ที่เจ้าของโปรเจกต์บันทึก ปรับค่า "1 C" ในข้อ 1.2 แล้วแก้ข้อ 1.3 ในไฟล์นี้
- ถ้าเหลือ > 30% ปลายสัปดาห์ → เพิ่มชุดตรวจศาสนา ถ้าชนก่อนวันที่ 5 → ลดเหลือ 3 ชุด

### 1.6 เมื่อ Claude ชนลิมิต

- **Codex ทำต่อได้:** ทุกแพ็กเกจที่ไม่มีเนื้อหาศาสนา (โค้ด, SEO, CI, ภาพสิ่งของ, วัด DOM, ร่างคำแปล UI)
  เก็บงานใน worktree ของตัวเอง ไม่ merge เอง
- **รอ Claude:** ทุกบรรทัดที่เป็นอายะฮ์/หะดีษ/ดุอาอ์/ฟัตวา, ภาพที่มีคนหรือสัตว์, การรวมเข้า branch หลัก
  Codex ใส่ไว้ในคิว `docs/briefs/QUEUE.md` หัวข้อ "รอ Claude"
- **ห้าม commit โดยไม่มีเจ้าของโปรเจกต์** ไม่ว่ากรณีใด (`AGENTS.md` ข้อ 5)

## 5. Handoff — วิธีทำงานกับ Codex

### 5.1 วิธีเรียก (กฎที่เคยเสียงานมาแล้ว)

รันผ่าน **Bash tool (Git Bash)** เท่านั้น — ใน PowerShell `timeout` เป็นคนละคำสั่ง จะไม่จำกัดเวลา

```bash
timeout 5400 codex exec -m gpt-6.1-sol -s workspace-write -C D:/Littleummah-<ID> \
  "$(cat D:/Littleummah/docs/briefs/<ID>.md)" < /dev/null
# งานอ่านอย่างเดียว (P0-1, P1-4): ใช้ -s read-only แล้วให้ Codex พิมพ์รายงานออกมา Claude เป็นคนบันทึกไฟล์
# แนบภาพอ้างอิง: ใส่ prompt ก่อน แล้วค่อย -i <ไฟล์ภาพ> (รูปแบบที่ใช้ได้ในงานเกาะสำรวจ)
```

- **ต้องมี `-m` ทุกครั้ง** · **ต้องมี `timeout`** · **ต้องปิด stdin `< /dev/null`**
  (16 ต.ค. เสียงาน 50 นาที เพราะค้างที่ "Reading additional input from stdin...")
- **ต้องมี `-s workspace-write`** สำหรับงานที่แก้ไฟล์ — ไม่ใส่แล้ว Codex อาจแก้ไฟล์ไม่ได้ ทั้งรอบเสียเปล่า
- path ของ brief ใช้ **absolute path** — `$(cat ...)` อ่านจากโฟลเดอร์ของ shell ไม่ใช่จาก `-C`
- ทำงานใน **worktree แยกต่อแพ็กเกจ** (`git worktree add D:/Littleummah-<ID> -b codex/<ID> main`) หรือ `output/` สำหรับงานออกแบบ/รายงาน
- worktree ใหม่ต้อง `npm ci` เอง · ห้ามแตะ worktree ที่มีงานค้างของคนอื่น

### 5.2 แม่แบบ brief (คัดลอกไปที่ `docs/briefs/<ID>.md`)

```markdown
# <ID> — <ชื่องาน>
อ่าน AGENTS.md ทั้งไฟล์ก่อน โดยเฉพาะข้อ <…> และอ่าน node_modules/next/dist/docs/ ส่วนที่เกี่ยวก่อนเขียนโค้ด Next
## ขอบเขต
- ทำ: …
- ไม่ทำ: …
## ไฟล์ที่แก้ได้
- … (นอกนี้ห้ามแก้ — ถ้าจำเป็นให้หยุดแล้วรายงาน)
## เกณฑ์ผ่าน
- npm run verify ผ่าน
- …
## ห้าม
- commit / push / reset / ลบไฟล์ที่ไม่ได้สร้างเอง
- ตัดสินเนื้อหาศาสนา (ติดป้าย REVIEW-RELIGIOUS แล้วข้าม)
- ใส่ emoji คน/สัตว์, สัญลักษณ์ดนตรี, ใบหน้าบนสิ่งมีชีวิต
## เวลา
<นาที> — ถ้าไม่ทันให้หยุดแล้วส่งรายงานสิ่งที่ค้าง
```

### 5.3 รูปแบบรายงานของ Codex (บังคับ — ให้ Claude อ่านเร็ว)

```markdown
## <ID> รายงาน
- สถานะ: เสร็จ / เสร็จบางส่วน / ติด
- branch/worktree: …
- ไฟล์ที่แก้: (รายการ + 1 บรรทัดต่อไฟล์)
- ผลตรวจ: verify ✅/❌ (ถ้า ❌ แปะ error 20 บรรทัดสุดท้าย) · verify:browser · อื่นๆ
- จุดเสี่ยงที่ Claude ควรดู: (ไฟล์:บรรทัด ไม่เกิน 5 จุด)
- REVIEW-RELIGIOUS: (จำนวน + ที่อยู่ไฟล์หลักฐาน) หรือ "ไม่มี"
- ภาพใหม่: (path + ภาพ crop ศีรษะ + ผล alpha) หรือ "ไม่มี"
- คำถามให้เจ้าของโปรเจกต์: …
```

### 5.4 ลำดับต่อแพ็กเกจ

1. Claude เขียน brief → 2. Codex ทำ + ตรวจตัวเอง + รายงาน → 3. Claude รัน `npm run verify` และอ่านจุดเสี่ยง
→ 4. Codex อีกรอบ review diff (`AGENTS.md` ข้อ 5) → 5. Claude สรุปให้เจ้าของโปรเจกต์ (บอก model ที่ใช้) → 6. เจ้าของโปรเจกต์อนุมัติ → commit

### 5.5 ใช้ astra เมื่อ

layout ที่ต้องลงทั้งมือถือแนวตั้ง/แนวนอน/แท็บเล็ต · งานหลายส่วนพร้อมกัน (motion + responsive + พิกัดบนภาพเกาะ)
· sol ลองแล้วไม่จบ · ออกแบบ flow/หน้าใหม่ทั้งหน้า (P1-4, P4-1, P5-1) — นอกนั้นใช้ sol

**หลัก: คุณภาพก่อนโควต้า (เจ้าของโปรเจกต์ตัดสิน 7 พ.ย. — จะซื้อโควต้า Codex เพิ่ม)**
astra กินโควต้าราว 2 เท่าของ sol แต่ไม่ใช่เหตุผลให้เลือก sol ถ้างานนั้นต้องใช้วิจารณญาณ
1. **astra** — ทุกงานที่มีการตัดสินใจหรือมีผลกับเด็กโดยตรง: LS-1, P1-1 (เลือกฟอนต์), P1-2 (เลือกภาพ OG/ข้อความแชร์), P1-3 (หน้าที่เด็กเห็น),
   P1-4, P1-5, P2-1 (ร่างอังกฤษ), P3-1, P4-1, P5 ทั้งหมด, review diff ข้อ 5 ของงานที่ซับซ้อน
2. **sol (medium)** — เฉพาะงานกลไกที่ตรวจผลได้ชัดและไม่มีทางเลือกให้ชั่ง: P0-3 (แก้ selector ตามหน้าจริง), P0-4 (ย้ายไฟล์), P3-2 (รันสคริปต์อัดเสียง), review diff เล็ก
- ไม่ใช้ `model_reasoning_effort=low` · งานยากมาก (layout หลายจอ, flow ใหม่) ใช้ astra + `-c model_reasoning_effort=high`
- ข้อจำกัดเวลา (`timeout`) ตั้งให้พอทำดี ไม่ตั้งสั้นเพื่อประหยัด
- ระบุ model + ระดับคิดไว้บรรทัดแรกของทุก brief
